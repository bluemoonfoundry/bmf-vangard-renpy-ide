# Parser Corpus, Analysis Benchmarks and Stale-Request Cancellation

**Status:** Draft (pending review)
**Date:** 2026-10-24
**Beads:** `bmf-vangard-renpy-ide-nms4.3` (parent epic `nms4`; prepares for `r7pn`). Closes grammar bugs it fixes along the way (see §3.4).

## Intent

`r7pn` will replace the regex analyzer behind `useRenpyAnalysis` with the tree-sitter AST. That rewrite needs three safety nets first, which is what `nms4.3` is (owner's framing):

1. **A parser corpus** broad enough that grammar changes made for `r7pn` cannot silently break real Ren'Py.
2. **Recorded performance numbers** for today's analysis so the rewrite can be compared against them.
3. **Correct cancellation** in the analysis worker, so an outdated request can never overwrite a newer one.

Acceptance criteria (from the issue): corpus covers each listed category; benchmark numbers recorded for three fixture sizes; superseded analysis requests are cancelled and never overwrite newer results.

## Goals

- Corpus cases for: valid Ren'Py, common project idioms, malformed / half-typed editor text, screens, ATL, Python blocks, translations, and nested constructs.
- Grammar bugs that the new cases hit are **fixed in the grammar on the spot** (owner's decision), not recorded as broken trees and not skipped.
- Benchmarks on three fixture sizes: small, medium, large. **Numbers are recorded, not enforced**: no CI gate (owner's decision).
- Worker cancellation that guarantees **correctness**: a superseded request stops at the next check, posts nothing, and writes no cache (owner's decision: correctness is enough; checks only between steps).

## Non-goals

- **Cold project open timing.** Explicitly out (owner's decision).
- **Responsiveness work.** No checks inside the regex phases, no chunking of `performRenpyAnalysis`, no change to the 500 ms debounce.
- **CI performance gates** or regression thresholds.
- **Switching consumers to the AST.** That is `r7pn`.
- **Renderer changes.** `useRenpyAnalysis` already drops replies whose id is not the latest and derives `isPending` from its own latest request (vod9, `e6c1c00`). It stays as is.
- **Memory / bundle / load benchmarks.** That is `b70a.4.1`, which reuses this work's fixture generator.

## Anti-goals

- A benchmark that measures something other than the code the app actually runs (e.g. a hand-copied analysis loop).
- Fixtures that differ between runs, making numbers incomparable.
- Corpus expectations copied from the parser output without checking they are the *right* tree. A corpus that enshrines wrong parses is worse than none.
- A grammar fix that makes a new case pass by regressing an existing one, or that changes node/field names the symbol index (`blockContribution`, `renpyWalk`, `pythonWalk`, `parseBlock` injections) relies on without updating those consumers in the same change.

## Constraints

- Corpus cases live in `tree-sitter-renpy/test/corpus/*.txt` in standard `tree-sitter test` format, so both `npm test` (via `src/test/treeSitterCorpus.test.ts`, against the committed `renpy.wasm`) and `npm --prefix tree-sitter-renpy test` run them.
- Grammar changes must keep `renpy.wasm` reproducible: rebuild with `npm run build:grammar` (tree-sitter-cli 0.24.7, emscripten 3.1.64 via Docker; Docker is available on the dev machine), commit the regenerated `src/parser.c`, `renpy.wasm` and `wasm-provenance.json`, and keep `npm run check:grammar` passing.
- Windows dev machine; Git Bash. Benchmarks must run there.
- Repo conventions: `@/` imports, Vitest, bd for tracking.

## Design

Work happens in this order (my call): **benchmarks (§2) first**, so the baseline is measured on code without cancellation; then **cancellation (§1)**; then **corpus and grammar fixes (§3)**. Each part is its own commit (or commit series) on one feature branch. Sections keep their numbers for reference.

### 1. Cancellation (worker)

**Today** (`src/workers/analysisRequestHandler.ts`, `renpyAnalysis.worker.ts`): every request runs to completion. The regex phases are synchronous; only the symbol-index step (`updateProjectIndex`) awaits, per block. When two requests overlap there, whichever finishes last sets `cachedSignatures`/`cachedResult` and the contribution cache, even if it is the older one. The renderer ignores the stale reply, so nothing wrong is shown, but the worker cache can regress to older content.

**Change:**

- The handler tracks the **last request to arrive** as the newest (my call). It does not compare ids numerically: `requestIdRef` is per hook instance, so ids restart at 1 if the hook remounts, and a "highest id wins" rule would then cancel every new request.
- A running request asks "am I still the newest?" **between phases** (parse, routes, translations, index, finalize) and **between blocks** inside the index build. If not, it stops there.
- A stopped request posts **nothing** (no progress, no result, no error) and writes **neither** `cachedSignatures`/`cachedResult` **nor** the contribution cache.
- For the check to ever see a newer request, the worker must let the event loop process incoming messages. Insert a real macrotask yield at the check points that sit between awaits (at least once before the index step and periodically between index blocks). The exact mechanism (`setTimeout(0)`, `MessageChannel`, `scheduler.yield` where available) and how often to yield between blocks are left to the builder; keep the overhead small enough that the benchmark numbers for a single uncontested request don't move noticeably.
- `updateProjectIndex` gains a way to be told to stop (e.g. an `isCancelled` / `AbortSignal`-style dep). On cancellation it must not assign `cache.byBlockId`. It rejects or returns a sentinel; the handler treats that as "stopped", not as an index error (no `indexError`, no warning).
- The content-hash fast path (unchanged signatures, cached result returned immediately) is unaffected.

**Tests** (unit, in the style of the existing handler tests, with a fake slow `updateIndex`):
- Request A is mid-index when request B arrives → A posts nothing after B arrives, B's result is posted, and the handler's cached result/signatures equal B's.
- A cancelled request never assigns the contribution cache (`updateProjectIndex` with a cancel dep).
- An uncontested request behaves exactly as today (progress sequence and result).
- A newer request whose content equals the cached result still hits the fast path after an older request was cancelled.

### 2. Benchmarks

**Fixtures.**
- **Small:** the existing `DemoProject/game` (7 `.rpy` files, ~2.4k lines). Used as-is.
- **Medium:** ~50 files / ~20k lines. **Large:** ~300 files / ~150k lines. (Sizes are my call.) Both generated, not committed (owner's decision: generated content is fine).
- A **generator** (e.g. `scripts/generate-bench-project.mjs` or a TS module under `src/test/bench/`; location is the builder's call) produces a project from a size preset and a **fixed seed**, so the same preset always yields byte-identical output. It must be importable/reusable by `b70a.4.1`.
- Generated scripts mix realistic Ren'Py: labels with local labels, cross-file `jump`/`call`, menus with conditions, say lines with speakers, attributes and `[var]` interpolation, `define`/`default`, `$` lines and `python:`/`init python:` blocks with functions, `show`/`scene`/`with`/ATL, screens with `use`, and `translate` blocks. Content only needs to be plausible, not a coherent story. Generated content should parse without errors under the grammar as it stands at baseline time; if the generator naturally hits a known grammar bug, avoid that construct in the generator rather than block the baseline.

**Scenarios** (per fixture size):
1. **Full analysis, regex path:** `performRenpyAnalysis` + `performRouteAnalysis` + `performTranslationAnalysis` as the worker runs them.
2. **Full analysis, symbol index only:** `updateProjectIndex` from an empty cache.
3. **One-file edit:** a warm worker/cache, then one file's content changes; time the whole request (regex phases + incremental index, where only that file is re-parsed).

Prefer driving scenarios 1 and 3 through `createAnalysisRequestHandler` so the benchmark runs the same code the worker runs (anti-goal above). Each scenario runs several times after a warm-up and reports the median (plus min/max).

**Harness.** One npm script (e.g. `npm run bench`), **not** part of `npm test` or `npm run gate`. Vitest's `bench` mode or a plain Node/tsx script are both fine. Builder's call, but it must load `renpy.wasm` the same way the tests do.

**Recording.** A markdown doc in the repo (e.g. `docs/benchmarks/analysis-baseline.md`) with a table per scenario × size, plus machine (CPU, RAM, OS), Node version, date and commit. A short summary goes on the `nms4.3` bd issue. Three columns, each from the same generated fixtures (like-for-like, my call):
1. **Baseline**: before cancellation and before any grammar change.
2. **After cancellation**: confirms the yields don't noticeably slow an uncontested request.
3. **After grammar fixes**.

The generator documents each construct it avoids at baseline because of a known grammar bug. Once those bugs are fixed, it gains an option that enables them, and the post-fix run records that variant as an extra row (not a replacement for the like-for-like column), so the fixed code paths are exercised at scale too.

### 3. Corpus expansion and grammar fixes

**Today:** 18 corpus files, ~55 cases. Thin: menus, say, control-flow and image statements have one case each; malformed/half-typed text has 4 cases (`error-recovery.txt`); nested constructs have no dedicated cases.

**3.1 Cases to add** (into existing files where one fits, new files otherwise):
- **Common idioms:** say with attributes, `with`, and interpolation; `show … at … with …`; `scene`/`hide`; `call … from …`; menu with caption, conditional choices (`if`), and `set`; `if`/`elif`/`else`; `while`; `pass`; `return` with value; `voice`, `play`/`queue`/`stop` audio; `define` with `Character(...)` keyword arguments; `image` with ATL body.
- **Half-typed editor text:** dangling `jump` / `call` with no target; open `[` in a string; half-written `if` condition; menu choice with no body; `python:` header with nothing under it; `screen` header with unclosed parameter list; trailing `$` with nothing after. For each, the expected tree must keep the error **local**: statements before and after still parse as their proper nodes.
- **Nested constructs:** menu inside `if` inside label; local labels inside labels with jumps between them; ATL inside `show`; screens that `use` others with nested `vbox`/`hbox`/`if`/`for`; `python:` inside `init`; `translate` blocks containing say and `old`/`new` strings.
- **Screens, ATL, Python blocks, translations:** a few more realistic cases each (screen properties with expressions and `action`; ATL `parallel`/`block`/`choice`/`on`; Python with docstrings, `with … as`, decorators, classes; `translate` language blocks and string translations).
- `bmf-vangard-renpy-ide-f3dw` (say followed by a separate `with` statement) is folded in.

**3.2 Expected trees** are written from what the grammar should produce, checked by hand against Ren'Py semantics, not pasted from parser output without review.

**3.3 Grammar fixes.** When a new case exposes a grammar bug, fix it in `tree-sitter-renpy/grammar.js` / `src/scanner.c` in the same branch, rebuild the WASM (Constraints), and update any symbol-index consumer whose node shapes change, with its unit tests.

**3.4 Known bugs expected to be hit** (each fix closes its issue; one commit per fix):
- `nms4.14`: screen-language properties split at whitespace. **Grammar only** (owner's decision): group property name/value pairs and control-flow headers (`for … in …:`, `if …:`) so each value is one injected Python expression, and words like `in`/`action` stop being recorded as reads. Making screen-local names (`for` targets, screen parameters) resolve needs screen scope in the symbol index; that is out of scope and goes in a new issue.
- `nms4.15`: valid Python in `python:` bodies sets `hasError` (docstrings, `with … as`). **Opaque body** (owner's decision): `python:` / `init python:` (and equivalent Python-block) bodies become a single opaque indented node in the grammar, not Ren'Py statements. Update `queries/injections.scm`, the `parseBlock` injection handling, `blockContribution`'s `hasError`, and the expected trees of existing Python-block corpus cases in the same change. This is a planned change, not a "redesign" under the exception below.
- `q85r`: `[var]` brackets in screen-language strings break the tokenizer. **Decompose like say text** (owner's decision): screen-language string values split `[...]` into the same interpolation nodes `say_statement` text uses, and the symbol index records those reads, with tests. This is an intended behaviour change.
- `lssz`: `define`/`default`/`image` values break on quoted strings containing `#`.
- `aj2e`: `at_expr`/attributes can't parse `Transform(...)` calls.
- `rsxn`: comment as first line of a block can't establish indentation.
- `3nk7`: leading blank line before first statement gives a spurious top-level ERROR.

Not in scope unless a new case directly needs it: `dsuc` (P4, dynamic-precedence quirk) and `ugb1` (P4, `parseBlock` dedent, not grammar). If a newly found bug turns out to need a grammar redesign rather than a fix, file it as a new issue, leave that one case out with a note pointing at the issue, and tell the owner. That is the only allowed exception to "fix on the spot".

## Done when

- All new corpus cases pass under both `npm test` and `npm run check:grammar`; existing cases still pass; symbol-index tests still pass.
- Each bug fixed in §3.4 is closed with a reference to its commit.
- `docs/benchmarks/analysis-baseline.md` has baseline, after-cancellation and after-grammar-fix numbers for small/medium/large across the three scenarios, plus the post-fix row for the fuller generator variant; summary on the bd issue.
- A new bd issue exists for screen-scope resolution in the symbol index (from `nms4.14`).
- Cancellation tests pass; `npm run gate:checks` passes.
